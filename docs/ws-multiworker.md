# WebSocket при нескольких Uvicorn-воркерах

В production по-прежнему используются `UVICORN_WORKERS=4`.

## Схема

- Подключения WebSocket физически принадлежат конкретному воркеру.
- `Redis Pub/Sub` доставляет события всем воркерам; каждый отправляет их только
  локальным вкладкам указанных пользователей.
- Общие онлайн-статусы хранятся в Redis: уникальная аренда на вкладку, TTL 90 секунд,
  атомарные операции регистрации и отключения через Lua.
- PostgreSQL — источник истины для истории сообщений.
- Клиент после повторного соединения обновляет список чатов и историю открытого чата.

## Проверки

Единый GitHub Actions workflow `.github/workflows/ci.yml` запускает:

- Backend job с Redis 7: интеграционные тесты независимых WebSocket-менеджеров
  и четырёх отдельных Python-процессов;
- PostgreSQL 16 migrations + FastAPI HTTP smoke с JWT и Redis;
- отдельный `docker_compose` job: production Compose, **4 Uvicorn-воркера**,
  RSA-ключи, HTTP smoke, перезапуск и сохранность состояния.

Это подтверждает четырёхворкерный запуск и HTTP-операции, но не заменяет
полноценные браузерные E2E тесты реального WebSocket при отказах Redis.

Для локального запуска:

```bash
docker run --rm -d --name itmessage-redis-test -p 6379:6379 redis:7-alpine
cd backend
REDIS_INTEGRATION_TESTS=1 REDIS_INTEGRATION_URL=redis://localhost:6379/15 \
  python -m unittest discover -s tests -p 'test_integration_*.py' -v
cd ..
docker stop itmessage-redis-test
```

Для production-smoke:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.prod.yml logs -f backend
```

В двух браузерах под разными аккаунтами проверьте:

1. Вход, новые чаты и сообщение в обе стороны.
2. Несколько вкладок у одного пользователя: закрытие одной не делает его offline.
3. Переподключение WebSocket: список чатов и история обновляются.
4. Отключение Redis и последующее восстановление: Pub/Sub подписки возвращаются.
5. Принудительная остановка одного воркера: устаревший online исчезает после TTL.

## Восстановление после сбоя Redis (PR #13)

Фоновая задача Pub/Sub при сетевой ошибке повторяет подписку. Ошибки при
повторном получении клиента, `subscribe()` или закрытии старого Pub/Sub не
должны навсегда останавливать подписчик. Если Redis недоступен после commit,
ошибка push не превращает уже сохранённое сообщение в HTTP 500.
При сбое Redis во время WS heartbeat соединение закрывается с кодом `1012`;
локальная вкладка отвязывается, а недоступная Redis-аренда истекает по TTL.

## Известные ограничения

Redis Pub/Sub не хранит сообщения для отключённых подписчиков. Если Redis
недоступен после `commit`, HTTP-операция остаётся успешной, а подписчики
догоняют состояние через API после переподключения. Отдельный online-status
по TTL при аварии воркера перестаёт показываться в GET, но push-уведомление
`offline` автоматически не отправляется.

Для строгой гарантии push-доставки нужен durable outbox/stream и
клиентские идентификаторы подтверждений. Для быстрых reconnect presence-события имеют монотонную версию Redis;
клиент игнорирует опоздавшие обновления (N19).
