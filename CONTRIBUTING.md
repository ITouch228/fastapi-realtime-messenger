# Разработка ITMessage: ветки, коммиты и PR

Цель: **одна линейная ветка `main`**, небольшие проверяемые PR, единый стиль сообщений, отсутствие временных веток после слияния.

## Ветки

- `main` — стабильная ветка; без прямых рабочих коммитов.
- Временные ветки: `feat/<topic>`, `fix/<topic>`, `test/<topic>`, `docs/<topic>`, `refactor/<topic>`, `chore/<topic>`.
- Одна задача = одна ветка = один PR; при слиянии удалять head-ветку.
- Перед merge проверять, что branch не отстаёт от `main`, и все required CI jobs зелёные.

## Единый формат сообщений

Новые **squash-коммиты в `main`** оформляем в стиле Conventional Commits с русским описанием:

```text
<type>(<scope>): <краткое действие в инфинитиве> (#<PR>)
```

Типы: `feat` — функциональность, `fix` — исправление, `test` — тесты, `docs` — документация, `refactor` — рефакторинг, `chore` — обслуживание, `ci` — pipeline. `scope` можно опустить.

Примеры:

```text
fix(ws): восстановить подписку Redis после разрыва (#13)
test(docker): проверить четыре Uvicorn-воркера (#12)
docs: обновить архитектуру и документацию (#14)
```

Заголовок PR в том же стиле, но без номера PR, если GitHub добавит его при squash автоматически. Длина первой строки желательно до 72 символов; тело (при необходимости) объясняет **почему**, а не повторяет diff. Для релизных коммитов допускается `chore(release): vX.Y.Z`, когда действительно создан релиз.

Исторические коммиты `v1.0`–`v3.2` и Squash PR #1–#13 оставлены неизменными. **Не выполняйте `git rebase -i` / force push `main` только ради унификации текстов:** сменятся SHA и нарушится история клонированных репозиториев и ссылок на PR. Единый формат действует с новых PR.

## Перед созданием PR

```bash
python -m pip install -r backend/requirements-dev.txt
python -m pre_commit install
npm ci
cd backend
ruff check .
ruff format --check .
mypy --package app
python -m unittest discover -s tests -p 'test_*.py' -v
```

CI включает дополнительные PostgreSQL/Redis интеграции и Docker Compose smoke. Не запускать smoke-тесты на рабочей БД: они создают тестовые данные. После слияния — Squash and merge, Delete branch, затем локально:

```bash
git switch main
git pull --ff-only
git fetch --prune
```

Локальную ветку, если она больше не нужна и изменения сохранены в `main`, удаляйте через `git branch -d <branch>` (после squash Git иногда не считает её слитой; сначала проверьте состояние перед использованием `-D`).
